\section*{Project description}
ReSTIR reduces noise in direct-lighting estimates by reusing light samples across pixels and frames~\cite{bitterli2020restir}.
However, neighboring pixels can differ in geometry, materials, and visibility, limiting the benefit of spatial reuse.
We will study whether more selective spatial reuse reduces image error under the same GPU time budget, and how this tradeoff changes during camera motion.

We will reproduce a ReSTIR direct illumination (DI) baseline and compare it with two spatial reuse extensions: PDF Similarity~\cite{tokuyoshi2023similarity}, which rejects reuse between dissimilar target probability density functions (PDFs), and compatibility-guided neighbor selection (CGNS)~\cite{junkins2026cgns}, which uses weighted stochastic sampling to favor geometrically compatible neighbors.
Each extension will be evaluated separately against the shared baseline on Cornell Box, Bistro, and Arcade.

We have selected RTXDI v3.1.0~\cite{rtxdi} on Windows with Direct3D 12 and verified Cornell Box and Bistro captures using the official renderer.
These establish the rendering environment; algorithm extensions and controlled comparisons remain to be completed.
We will extend the sampling shaders and experiment tools to support three selectable methods, linear HDR output, and GPU timing records.

\section*{Key challenges}
\begin{itemize}
\item \textbf{Correct Weights for Reservoir Reuse.} Reused samples must be evaluated at the receiving pixel, with consistent reservoir normalization and visibility handling. Incorrect weights or unaccounted neighbor selection probabilities can introduce brightness errors or unintended bias.
\item \textbf{Adapting Spatial Reuse Strategies.} PDF Similarity needs reliable distribution estimates and safeguards when history becomes invalid. CGNS must be transferred from its path-tracing implementation to DI while preserving stochastic selection and the associated weighting assumptions.
\item \textbf{Measuring Quality at Equal Cost.} Distribution estimation and neighbor selection introduce additional computation. We must include this overhead when comparing image error at the same GPU time budget.
\item \textbf{Evaluating Reuse during Camera Motion.} Camera motion changes visibility and exposes surfaces without valid history. We need corresponding reference frames to distinguish sampling artifacts from changes in the scene's appearance.
\end{itemize}

\section*{Design and implementation details}
\textbf{Shared Renderer for Controlled Comparisons.}
We will reuse RTXDI's scene loading, ray tracing, and display infrastructure, while modifying reservoir reuse and adding the two extensions.
All methods will share the DI target, scenes, cameras, and materials; initial sampling and shading will remain fixed where compatible.
We will isolate the baseline from additional RTXDI features and document any required differences in temporal reuse.

\textbf{Spatial Reuse Extensions.}
PDF Similarity will estimate target distributions and reject ineffective reuse, with history safeguards during motion.
CGNS will use geometric compatibility to weight stochastic neighbor selection, adapting the Falcor-based author implementation~\cite{cgnsCode} to DI.
We will check each extension's selection probabilities and reservoir weights before comparing performance; combining the extensions is optional.

\textbf{Scenes and Reference Images.}
We will use Cornell Box for correctness checks, Bistro for complex geometry, and Arcade for varied materials and emissive surfaces~\cite{rtxdiAssets}.
We plan one static view per scene and one or two short camera trajectories overall.
References will use a conventional high-sample DI estimator with convergence checks and matching scene settings.

\textbf{Quality, Cost, and Temporal Behavior.}
The current runner saves preview images and run metadata; we will add linear HDR export, explicit seed control, and GPU timing collection.
At fixed resolution, equal-time comparisons will include method-specific overhead and report pass times, total rendering time, and memory use.
Image error will be measured before denoising or tone mapping, with definitions and normalization fixed before evaluation.
Each run will record the resolved configuration, code and scene revisions, seeds, and GPU environment.
Independent seeds will quantify variability; sequence tests will cover history start-up, steady state, and disocclusion against corresponding reference frames.
Ablations will vary candidate count, temporal reuse, spatial reuse, and neighbor count separately.

\textbf{Implementation Responsibilities and Deliverables.}
Provisionally, one member will lead the renderer and baseline, and the other scene setup and evaluation; we will divide the extensions and review each other's code.
Deliverables include three selectable methods, a demo, and a report supported by reproducible configurations and run records, with one experiment repeated on the teammate's machine.
We will identify upstream code, our adaptations, and AI assistance.
If time becomes limited, we will reduce optional parameter sweeps before changing the three-method target.
